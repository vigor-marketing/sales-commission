## 2. 当前线上访问地址

| 场景 | 地址 |
|---|---|
| 前端入口 | `http://1.15.91.150/apps/sales-commission/`（工作台同源代理，带 auth） |
| 后端（本机） | `http://127.0.0.1:18081` |
| 健康检查 | `http://127.0.0.1:18081/api/health` |

前端通过 nginx `location /apps/sales-commission/` 代理到本机 18081，`/apps/sales-commission/api/` 则 rewrite 到 `/api/*` 后再代理到 18081，均经 `auth_request` 校验工作台会话。

### 2.1 访问异常优先检查

1. `curl http://127.0.0.1:18081/api/health` 确认后端在线。
2. `systemctl status vigor-sales-commission.service` 确认服务 active。
3. `sudo nginx -t && systemctl status nginx` 确认 nginx 正常。
4. 前端页面强刷（浏览器缓存旧 JS 时可能看不到最新功能）。

### 3.1 架构说明

```text
nginx（80）
 ├─ /apps/sales-commission/       → 127.0.0.1:18081（静态前端 + API）
 ├─ /apps/sales-commission/api/   → 127.0.0.1:18081（rewrite 后走 /api/*）
 └─ auth_request                  → 工作台 BFF 会话校验
         ↓
Express + SQLite（18081）
 ├─ 业务写入 → 本地快照 + COS 上传（防抖 800ms）
 └─ 定时兜底：每 10 分钟（应用内）+ 每 6 小时（systemd timer）
```

## 5. COS 正式生产备份资料

### 5.1 存储边界

| 存储体系 | 当前用途 | 是否参与生产备份 |
|---|---|---|
| 独立 COS 桶 `knowledge-base-1459141414`（ap-shanghai） | 运行数据库正式备份与恢复 | 是 |
| 本机快照 `/var/lib/vigor-sales-commission/backups/` | 本地兜底 | 是 |
| 旧 CloudBase 传统 COS（`monktestcloud-…`） | 已弃用（凭据失效） | 否 |

### 5.2 对象命名

正式主备份对象（COS 桶 `knowledge-base-1459141414`）：

```text
sales-commission/财务数据.db
```

本地快照：

```text
commission-YYYY-MM-DDTHH-MM-SS.db   （保留最近 56 份）
```

### 5.3 数据库与备份关系

```text
CVM 运行库 /var/lib/vigor-sales-commission/commission.db
 ├─ 业务写入 SQLite（WAL）
 ├─ 写后防抖 → 本地快照（better-sqlite3 在线备份）
 └─ 写后防抖 → COS 上传 sales-commission/财务数据.db（cos-nodejs-sdk-v5）
```

CVM 的 `/var/lib` 是持久盘，数据库本身不会因重启丢失；备份用于防误删/误改/磁盘损坏/整机丢失。

## 6. 自动备份与启动恢复

### 6.1 备份触发规则

| 触发时机 | 行为 |
|---|---|
| 收款/提成计算保存、合同变更/删除、系统设置保存、费用名变更、历史删除 | 防抖 800ms → 本地快照 + COS 上传 |
| 服务持续运行 | 每 10 分钟兜底（本地 + COS） |
| systemd 定时器 `vigor-sales-commission-backup.timer` | 每 6 小时独立本地快照 |

连续短时间写入会合并为一次上传，减少重复请求。

### 6.2 启动恢复顺序（仅当数据库文件缺失时）

1. 服务启动（`bootstrap`）。
2. 数据库文件缺失时，尝试从 COS `sales-commission/财务数据.db` 下载。
3. COS 失败/不存在 → 回退本地最新快照。
4. SQLite 文件头校验通过后，临时文件原子替换。
5. 初始化 schema，空库时补充种子数据。
6. 启动定时备份。

> 数据库文件已存在时**不覆盖**，避免旧备份盖新数据。

### 6.3 首次上线说明

COS/本地均无备份时，首次启动日志出现“未找到可恢复的云端/本地备份”属于初始化情形；首次写入后会立即产生本地快照与 COS 备份。

| 变量名 | 默认 |

备份子账号只应具备：目标 COS 桶的 `sales-commission/` 前缀读/写/列权限；不授予账号管理、云资源管理、全桶删除等无关权限。凭据若曾出现在不安全环境，应立即在腾讯云控制台禁用并重新创建，然后更新 cos.env 并重启服务。

## 8. 发布流程

### 8.1 本地验证

```text
npm run build                          # 前端构建
npm --prefix server run typecheck      # 服务端类型检查
npm --prefix server run test           # 服务端测试
```

### 8.2 发布前安全检查

确认以下内容没有进入提交或部署上下文：

- `server/data/*.db`、`*.db-wal`、`*.db-shm`
- 本地备份文件与导出文件
- `.env`、`.env.*` 中的真实凭据
- SecretId、SecretKey、API Key、密码或令牌

### 8.3 部署到 CVM

1. 构建前端（`VITE_APP_BASE=/apps/sales-commission/ npm run build`）与服务端（`tsc`）。
2. 将 `server/src`、`server/dist`、`client/src`、`client/dist` 同步到 `/opt/vigor-sales-commission/app/`。
3. `sudo systemctl restart vigor-sales-commission.service`。
4. 验证 health、备份日志、COS 对象更新时间。

### 8.4 发布后验证

- `curl http://127.0.0.1:18081/api/health` 返回 `{"ok":true,...}`。
- 前端页面刷新后能读取配置、录入合同、计算提成、历史与统计正常。
- 日志出现 `已写入云端备份: sales-commission/财务数据.db`，COS 对象更新。

## 9. 回滚与恢复演练

### 9.1 版本回滚

代码回滚：将上一版构建产物重新同步到 `/opt/vigor-sales-commission/app/`，重启服务。不要为排查问题直接删除 COS 主备份或本地快照。

### 9.2 受控恢复演练

涉及备份模块或数据库路径的重大修改后，在低业务时段执行：

1. 记录 COS 主对象与本地快照的最后修改时间和大小。
2. 在隔离环境验证备份文件能被 better-sqlite3 打开且数据完整。
3. 核对合同、收款计划、提成历史与系统设置仍存在。
4. 确认恢复后服务能重新上传主对象。

## 13. 已知边界与维护建议

- 独立 COS 桶 `knowledge-base-1459141414` 是当前正式生产主备份；本地快照为兜底。
- `/var/lib/vigor-sales-commission/commission.db` 是持久盘数据，但仍需备份防误删/损坏/整机丢失。
- 单实例 SQLite + COS 备份不适合高并发、多副本场景；业务量增长时应评估迁移托管关系型数据库。
- 备份数据库包含合同、收款和提成等业务数据，应保持私有读写。
- 每月检查一次 COS 对象与本地快照的存在性、最后修改时间、大小和日志结果。
- 凭据泄露、人员变更或权限扩大时，立即轮换凭据并重启服务。
