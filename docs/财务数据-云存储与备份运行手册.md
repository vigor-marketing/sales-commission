## 2. 财务数据对象命名

云端主备份对象使用业务专属名称：

```text
sales-commission/财务数据.db
```

旧路径仅用于历史兼容恢复：

```text
sales-commission/commission.db
```

系统启动时会先尝试恢复 `财务数据.db`；若该对象不存在，才尝试读取旧对象。写入备份时只更新主对象。旧对象确认不再需要后，可在 COS 控制台人工归档或删除；删除前应先确认最新主对象可下载且数据可打开。

## 3. 自动备份与恢复机制

### 自动备份触发

| 触发时机 | 行为 |
|---|---|
| 提成计算保存成功 | 延迟 800ms 上传数据库备份 |
| 合同删除成功 | 延迟 800ms 上传数据库备份 |
| 系统设置保存成功 | 延迟 800ms 上传数据库备份 |
| 云托管实例启动后 | 约 3 秒执行一次备份 |
| 服务持续运行 | 每 10 分钟执行一次兜底备份 |

连续写操作会被防抖合并，避免短时间重复上传。

### 自动恢复顺序

1. 容器启动。
2. 从传统 CloudBase COS 读取主备份 `sales-commission/财务数据.db`。
3. 若主备份不存在或无法通过 SQLite 文件头校验，尝试读取旧路径 `sales-commission/commission.db`。
4. 下载成功后使用临时文件原子替换本地数据库。
5. 初始化数据库结构并补充仅在空库时使用的种子数据。
6. 启动定时备份任务。

> PG Storage 的 `financial-data/财务数据.db` 不在上述链路中；它不是生产恢复来源，也不会接收自动备份。

> 说明：首次上线、COS 中尚无任何备份对象时，恢复日志可能显示“未找到可恢复的云端备份”；这属于首次初始化，不是故障。首次备份成功后，后续重启应从 COS 恢复。

## 4. 腾讯云配置参考

| 配置项 | 当前值 |

| 服务 | `sales-commission` |

| 最大实例 | 1 |
| 访问方式 | PUBLIC、OA、MINIAPP |

最小实例保持为 1，可以减少冷启动并保证定时备份持续运行；代价是持续产生云托管实例费用。

### 备份所需环境变量

在 CloudBase 云托管服务的环境变量中维护以下**变量名**，不要将变量值写入代码、文档、Git 或聊天记录。`PG_STORAGE_*` 变量不再是生产备份的必需配置；如需保留，应仅作为未来独立验证用途，且不得影响 COS 主链路：

| 变量名 | 用途 |
|---|---|
| `BACKUP_BUCKET` | CloudBase 云存储桶名称 |
| `BACKUP_SECRET_ID` | 有最小权限的腾讯云访问标识 |
| `BACKUP_SECRET_KEY` | 对应访问密钥 |
| `DB_PATH` | 容器运行时 SQLite 路径 |
| `NODE_ENV` | 生产环境标识 |

云托管运行环境使用 `CBR_ENV_ID` 自动识别 CloudBase 环境 ID。

### 最小权限建议

创建专用子账号或角色，仅授权以下范围：

- 目标 COS 存储桶；
- `sales-commission/` 前缀；
- 必需动作：读取、写入、列出对象；
- 禁止授予账号管理、计算资源管理、全桶删除等无关权限。

若密钥曾在非安全环境出现，应立即在腾讯云控制台禁用并重新创建，然后更新云托管环境变量并重新发布。

## 5. 日常检查

### 快速健康检查

打开以下地址，应返回 `{"ok":true,...}`：

```text
https://sales-commission-288305-10-1459141414.sh.run.tcloudbase.com/api/health
```

### 检查备份对象

在 CloudBase 控制台进入目标环境的云存储，查看：

```text
sales-commission/财务数据.db
```

重点确认：

- 对象存在；
- 最后修改时间在最近一次业务写入或 10 分钟兜底周期之后；
- 文件大小不为 0；
- 对象没有被设置为公网读取。

### 检查日志

在 CloudBase 控制台进入云托管服务 `sales-commission` 的日志，搜索 `backup`。重点关注：

- `已从云端恢复数据库备份: COS:sales-commission/财务数据.db`：已从正式主对象恢复成功；
- `已写入云端备份: sales-commission/财务数据.db`：已更新正式主对象；
- `COS 上传失败`：检查对象权限、环境变量和网络；
- `未找到可恢复的云端备份`：仅首次运行可接受；若已有备份则需要排查路径或权限。

检索日志时应限定为当前线上版本，旧版本残留实例的历史日志不应作为当前版本故障依据。

## 6. 发布更新流程

1. 在本地完成代码修改。
2. 执行服务端类型检查和测试：

```text
server: tsc --noEmit
server: vitest run
```

3. 确认不提交 `.db`、`-wal`、`-shm`、备份文件和任何密钥。
4. 使用 CloudBase 云托管将项目根目录部署至 `sales-commission` 服务。
5. 等待最新版本状态为 `normal` 且流量为 100%。
6. 访问健康检查接口。
7. 在 CLS 检查当前版本启动日志。
8. 到 COS 核对 `sales-commission/财务数据.db` 是否更新。

### 发布后的恢复演练

每次涉及备份模块或运行时路径的重大修改后，建议在低业务时段完成一次受控演练：

1. 记录 COS 主备份的修改时间与大小。
2. 正常发布一个不改变业务数据的版本。
3. 在新版本 CLS 日志中确认“已从云端恢复数据库备份”。
4. 使用页面或 API 核对合同、收款计划与提成历史仍存在。
5. 完成后确认新版本重新上传备份。

不要直接删除容器数据或 COS 对象进行测试。

## 7. 常见问题与处理

### 7.1 COS 目录为空

PG Storage 的 `financial-data` 桶与传统 CloudBase COS 是两套独立存储界面。请在传统 CloudBase 云存储中检查 `sales-commission/财务数据.db`，不要以 PG Storage 桶列表是否为空判断 COS 主备份状态。

检查顺序：

1. 云托管版本是否为 `normal` 并已接管流量；
2. 环境变量中是否存在备份桶和凭据变量；
3. CLS 是否有 `上传备份失败`；
4. 子账号是否具有该前缀的读、写、列权限；
5. 触发一次正常业务保存或等待 10 分钟兜底备份。

### 7.2 启动后未恢复旧数据

检查顺序：

1. COS 中主对象 `sales-commission/财务数据.db` 是否存在；
2. 若仍处于迁移阶段，旧对象 `sales-commission/commission.db` 是否存在；
3. 当前版本日志是否出现恢复成功记录；
4. `DB_PATH` 是否保持为 `/data/commission.db`；
5. 数据库文件大小是否异常小或为 0。

### 7.3 出现 `require is not defined`

这是 Node.js ESM 与 CommonJS 混用导致的运行时问题。备份模块必须使用静态 `import` 导入 CloudBase SDK，不能在 ESM 文件内调用 `require()`。

### 7.4 部署成功但页面/API 异常

按以下顺序排查：

1. 健康接口；
2. 云托管最新版本状态与 100% 流量；
3. 云托管启动日志；
4. 前端 `VITE_API_BASE` 是否仍指向线上后端；
5. SPA 路由回退与 API 跨域配置。

## 8. 新建存储空间确认规则

后续新增任何数据存储空间、备份目录、存储桶、数据库文件或导出文件前，必须先向业务负责人确认以下两项，未确认不得自行创建：

1. **存储位置**：确认云端/本地、具体服务（例如 COS、数据库或文件系统）、目标存储桶与完整目录路径。
2. **文件命名**：确认业务名称、文件扩展名、版本或日期规则，以及是否需要保留旧文件兼容路径。

确认后应在实施记录或本手册中写明最终路径和命名规则；名称、路径或用途发生变更时，必须再次确认。不得仅根据临时技术默认值、旧项目路径或相似业务自行推断。

## 9. 安全与维护规则

- 密钥只保存在腾讯云环境变量或受控密钥管理系统中。
- 禁止将密钥写入 Markdown、源代码、截图、终端输出、数据库或 Git 提交。
- COS 数据库备份包含业务与财务信息，应保持私有读写权限。
- 每月核对一次对象可访问性、最后修改时间和日志告警。
- 更换人员、泄露风险或权限扩大时，立即轮换密钥。
- 正式业务量增长或出现多实例并发需求时，应评估迁移到托管关系型数据库；单实例 SQLite + COS 备份不适合作为高并发、多副本数据库方案。
