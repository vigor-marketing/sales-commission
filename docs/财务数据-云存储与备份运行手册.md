# 财务数据：备份与恢复运行手册

> 适用系统：提成计算系统（sales-commission）
> 文档用途：说明当前 CVM 部署下 SQLite 数据库的备份与恢复流程。本文不记录任何 SecretId、SecretKey、令牌或密码。

## 1. 当前架构

| 层级 | 服务 | 说明 |
|---|---|---|
| 部署主机 | CVM `1.15.91.150` | 代码目录 `/opt/vigor-sales-commission/app` |
| 前端 | React（Vite 构建产物） | 经 nginx `/apps/sales-commission/` 同源代理（工作台 auth） |
| 后端 | Express + better-sqlite3 | systemd `vigor-sales-commission.service`，端口 18081 |
| 运行库 | SQLite（WAL） | `/var/lib/vigor-sales-commission/commission.db` |
| 主备份 | 独立 COS 桶 | `knowledge-base-1459141414`（ap-shanghai），对象 `sales-commission/财务数据.db` |
| 本地兜底 | 本机快照 | `/var/lib/vigor-sales-commission/backups/`，保留 56 份 |
| 进程管理 | systemd | 主服务 + `vigor-sales-commission-backup.timer`（每 6 小时） |

### 访问地址

- 前端：`http://1.15.91.150/apps/sales-commission/`（走工作台 auth_request）
- 后端：`http://127.0.0.1:18081`（仅本机，由 nginx 反代）
- 健康检查：`http://127.0.0.1:18081/api/health`

## 2. 备份对象命名

- COS 主对象：`sales-commission/财务数据.db`（桶 `knowledge-base-1459141414`，地域 `ap-shanghai`）。
- 本地快照：`commission-YYYY-MM-DDTHH-MM-SS.db`（时间倒序，保留最近 56 份）。

## 3. 自动备份与恢复

### 备份触发

| 时机 | 行为 |
|---|---|
| 任何写操作（计算/合同/设置/费用名/历史删除） | 防抖 800ms → 本地快照 + COS 上传 |
| 服务持续运行 | 每 10 分钟兜底（本地 + COS） |
| systemd 定时器 | 每 6 小时独立本地快照（应用外的兜底，即使应用未触发写） |

连续写操作会被防抖合并，避免短时间重复上传。

### 恢复顺序（仅当数据库文件缺失时才执行）

1. 尝试从 COS 下载主对象 `sales-commission/财务数据.db`。
2. COS 失败或不存在 → 回退本地最新快照。
3. 校验 SQLite 文件头（`SQLite format 3\0`）后原子替换（临时文件 rename）。

> 数据库文件已存在时绝不覆盖，避免旧备份盖新数据。

## 4. 环境变量（凭据）

凭据保存在 `/etc/vigor-sales-commission/cos.env`（权限 600，root 属主），经 systemd `EnvironmentFile` 注入，不写入代码、Git 或文档：

| 变量 | 说明 |
|---|---|
| `COS_BUCKET` | 独立 COS 桶名（含 APPID，如 `knowledge-base-1459141414`） |
| `COS_REGION` | 地域（如 `ap-shanghai`） |
| `COS_SECRET_ID` / `COS_SECRET_KEY` | 该桶 `PutObject`/`GetObject` 权限的子账号密钥 |
| `DB_PATH` | `/var/lib/vigor-sales-commission/commission.db` |
| `LOCAL_BACKUP_DIR` | 本地快照目录（默认 `{DB_PATH 目录}/backups`） |
| `LOCAL_BACKUP_KEEP` | 本地快照保留份数（默认 56） |

> 注：这套凭据为「最小权限」子账号，只应具备目标桶该前缀的读/写/列权限，禁止授予账号管理、全桶删除等无关权限。

## 5. 日常检查

### 快速健康检查

```text
curl http://127.0.0.1:18081/api/health   # 应返回 {"ok":true,...}
```

### 检查 COS 备份对象

在腾讯云 COS 控制台进入 `knowledge-base-1459141414`（ap-shanghai），查看 `sales-commission/财务数据.db`：

- 对象存在；
- 最后修改时间在最近一次业务写入或 10 分钟兜底之后；
- 文件大小非 0；
- 对象未设置为公网读取。

### 检查本地快照

```bash
sudo ls -la /var/lib/vigor-sales-commission/backups/
```

### 检查日志

```bash
sudo journalctl -u vigor-sales-commission.service --no-pager | grep backup
```

重点关注：

- `已写入云端备份: sales-commission/财务数据.db`：COS 上传成功；
- `已恢复数据库备份: COS:...`：从 COS 恢复成功；
- `已恢复数据库备份: 本地快照:...`：从本地快照恢复；
- `COS 上传失败`：检查 cos.env 凭据、桶权限与网络。

## 6. 发布更新流程

1. 本地改代码 → 服务端 `tsc --noEmit` + `vitest run`，前端 `npm run build`。
2. 提交并推送 GitHub。
3. 构建产物部署到 `/opt/vigor-sales-commission/app/`（server/src、server/dist、client/src、client/dist）。
4. `sudo systemctl restart vigor-sales-commission.service`。
5. 验证健康检查 + 备份日志 + COS 对象更新。

## 7. 安全与维护规则

- 密钥只存 `/etc/vigor-sales-commission/cos.env`（600），禁止写入 Markdown、源代码、截图、终端输出、数据库或 Git 提交。
- 密钥泄露或需轮换：在腾讯云控制台禁用旧密钥 → 更新 cos.env → 重启服务。
- COS 数据库备份包含业务与财务信息，保持私有读写。
- 每月核对一次对象可访问性、最后修改时间和日志告警。
- 正式业务量增长或出现多实例并发时，应评估迁移到托管关系型数据库；单实例 SQLite + COS 备份不适合高并发多副本场景。

## 8. 相关代码位置

| 文件 | 职责 |
|---|---|
| `server/src/services/backup.ts` | COS 上传/恢复 + 本地快照 + 定时任务 |

| `server/src/routes/*.ts` | 写操作后触发备份（scheduleBackup） |
